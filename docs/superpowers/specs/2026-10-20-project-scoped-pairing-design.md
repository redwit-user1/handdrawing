# 과제별 태블릿 연결 · 동기화 주기 조정 · 바뀐 쪽만 올리기 — 설계

작성 2026-10-20. 기준: 2B(앱 QR 연결)·2C(서버 기기 API)가 끝난 상태
(handdrawing `b083939`, Goono-ELN `8575daa74`, 브랜치 `claude/tablet-app-hand-drawing-sync-ofo0oi`).
기존 설계: `2026-10-17-goono-tablet-app-design.md`, 계약: `app/docs/SYNC-API.md`.

## 1. 왜

지금은 연구원이 마이페이지에서 스스로 QR을 띄워 기기를 연결하면, 그 기기가 연구원이 참여한 **모든** 편집 가능 과제에
노트를 만들고 올릴 수 있다. 과제 구성원 지정 말고는 연구책임자가 "이 과제를 태블릿으로 써도 되는지"를 정하거나 볼
방법이 없다. 관리·보안 면에서 태블릿 사용을 **과제 단위로 연구책임자가 허락하고 관리**해야 하고, 기기는 허락된 과제에만
올릴 수 있어야 한다(단방향 원칙 유지: 기기 → 서버만, 서버는 기기에 노트 내용을 내려보내지 않는다).

함께, 동기화·자동 버전 주기가 촘촘해 서버 요청과 연구노트 이력·저장 공간이 불필요하게 늘어나므로 주기를 늘리고,
버전마다 바뀌지 않은 페이지 그림까지 다시 저장하는 것을 없앤다.

## 2. 목표 / 비목표 / 반목표

목표
- 연구책임자가 과제 화면에서 과제 구성원 한 명을 골라 **그 과제 전용 1회용 QR**을 발급한다.
- 연구원이 앱으로 QR을 찍고, **본인이 구노 웹에서 승인**해야 연결이 완료된다(작성자 본인 확인).
- 연결은 **(기기, 연구원, 과제)** 단위. 한 기기에 여러 과제 연결을 둘 수 있고, 앱은 연결된 과제만 보여 준다.
  연결 안 된 과제에는 노트를 만들거나 올릴 수 없다(서버가 거부).
- 연구책임자는 과제 화면에서 그 과제에 연결된 기기를 보고 끊을 수 있다.
- 연결이 끊기면(책임자가 끊음·과제 종료·구성원 제외) 그 연결로 작성 중이던 노트의 **편집권이 자동으로 웹으로 돌아오고**,
  기기에 남은 올리지 않은 기록은 **미반영**으로 보관된다.
- 동기화 10분, 자동 버전 30분, 토큰 갱신 하루 1번.
- 버전을 올릴 때 **바뀐 페이지 그림만** 새로 저장한다.

비목표
- 사진을 버전마다 다시 넣지 않고 한 번만 저장하는 구조 변경(점검 A11) — 다음 단계.
- 기관 관리자의 기기 일괄 관리 화면, 특정 기기 ID 차단(DEVICE_NOT_ALLOWED는 계속 예약).
- 앱의 네이티브 배포(MDM/앱스토어) 방식.

반목표 (이렇게 되면 실패)
- 다른 사람이 연구원 명의로 연결할 수 있다(총괄 화면 QR을 아무나 찍어 연결 완료).
- 허락받지 않은 과제에 기기가 노트를 만들거나 올릴 수 있다.
- 연결이 끊긴 뒤 노트가 웹에서도 영영 "기기에서 작성 중"으로 묶여 있다.
- 기기에 쓴 필기가 사라진다(끊겨도 미반영으로 남아야 한다).
- 서버가 기기에 노트 내용을 내려보낸다.

## 3. 사람과 화면

### 3.1 연구책임자 (과제 화면)
- 발급·기기 목록·연결 끊기 권한: 그 과제의 책임자 역할(`PROJECT_MEMBER_ROLE_CCD` IN `PJ_MANAGER`, `PJ_LEAD_RESEARCHER`)
  **또는 그 과제의 총괄(`GNRL_YN='Y'`)** — 1단계 점검 유도(`inspectionNudge-mapper.xml` `sqlProjectScope`)와 같은 기준.
  기관 관리자는 이번 범위에서 발급하지 않는다.
- "태블릿 연결" 영역:
  - 구성원 목록에서 한 명(본인 포함 가능)을 고르고 **QR 만들기** → 과제 전용 QR + 코드 `XXXX-XXXX` + 남은 시간(5:00).
    QR은 1회용·5분, 같은 (과제, 연구원)으로 새로 만들면 이전 미사용 QR은 무효.
  - 이 과제에 연결된 기기 목록: 연구원, 기기 이름, 플랫폼·모델, 앱 버전, 마지막 접속, 상태(승인 대기 / 연결됨 / 끊김) +
    **연결 끊기**(확인 대화상자).
- 기관 스위치 `app.device.enabled=false`이면 영역 대신 "이 기관은 태블릿 연결을 사용하지 않습니다." 안내.

### 3.2 연구원 (앱)
- 첫 화면·다시 연결 화면은 지금처럼 "QR로 연결 / 코드 직접 입력". QR 형식은 그대로
  `goono-note://pair?server=…&code=…` (과제 정보는 서버가 코드로 안다).
- 찍으면 확인 단계: "**{과제명}** / 작성자 **{연구원 이름}** 으로 연결할까요?" → 연결 → **"구노 웹에서 승인을 기다리는 중"**
  화면(남은 시간 10:00, 취소 가능). 승인되면 바로 그 과제가 목록에 나타난다. 거절·만료되면 원인 안내.
- 이미 연결된 기기에서 새 과제 QR을 찍으면 **연결이 하나 더 추가**된다(같은 연구원일 때만. 다른 연구원의 과제 QR이면
  지금 규칙대로 올리지 않은 기록이 있으면 거부).
- 노트 목록·새 노트의 프로젝트 선택은 **연결된 과제만**. 과제별로 연결 상태가 다를 수 있다(한 과제만 끊김).
- 연결이 끊긴 과제의 노트: 편집 잠금 + 배너 "이 과제의 태블릿 연결이 끊겼습니다. 올리지 않은 기록은 미반영으로
  보관됩니다." 기록은 기존 "미반영 → 새 노트로 복원" 흐름으로 다른 연결된 과제에 옮길 수 있다.

### 3.3 연구원 (구노 웹 승인)
- 앱이 연결을 요청하면, 연구원이 구노 웹 **대시보드에 들어오면 모달**로 뜬다:
  "{과제명} 과제에 태블릿 '{기기 이름}'({플랫폼·모델})을 연결할까요? 요청 시각 {hh:mm}" — **승인 / 거절**.
  이미 대시보드에 있으면 다음 진입 또는 주기 확인 때 뜬다(빠른 반영 방식은 작성자에게 맡김: 폴링·웹 푸시 등).
- 승인 요청은 **10분** 유효. 지나면 앱에 "승인 시간이 지났습니다. 연구책임자에게 새 QR을 요청하세요."
- 연구원 본인만 승인할 수 있다(웹 세션 사용자 = 요청의 연구원).

## 4. 연결 수명과 규칙

1. 책임자 발급: 과제 코드 생성 = (과제, 연구원, 발급자) 묶음, 5분·1회용.
2. 앱 pair: 코드 확인(지금 규칙: 정규화, IP 실패 제한 공유, 평가 순서) → 코드 사용 처리 → **승인 대기 연결** 생성
   (기기, 연구원, 과제) → 앱은 대기 토큰/요청 ID로 상태를 조회(폴링 간격·방식은 작성자에게 맡김).
3. 연구원 승인 → 연결 활성. 이후 앱은 그 과제에 대해 기존 API(bootstrap·notes·versions·release)를 쓴다.
   거절 → 연결 폐기. 10분 경과 → 만료.
4. 활성 연결이 끊기는 경우: 책임자가 끊음 / 연구원이 과제 구성원에서 빠짐 / 사용 중지(4-5) / 다른 연구원이 기기 연결(4-2) /
   장기 미접속(4-4). 과제 종료는 끊김이 아니라 "중지"(4-1)지만 노트 처리는 같다.
   - 그 연결로 편집 위치가 기기인 노트 → **편집 위치 WEB**으로 되돌리고 이력에 남긴다(사유: 연결 끊김/과제 종료/구성원 제외).
   - 앱은 다음 동기화에서 그 과제가 끊긴 것을 알고, 그 과제 노트를 잠그고 대기 버전은 미반영으로 둔다.
4-1. **과제 종료·재개**: 과제가 편집 불가가 되면(진행 종료 후 유예 만료, 삭제, 사용 안 함) **하루 1번 작업**이 그 과제에서
   편집 위치가 기기인 노트를 WEB으로 되돌리고 이력(사유 "과제 종료")을 남긴다. 연결 자체는 지우지 않고 "과제 종료로 중지"
   상태로 둔다(요청 때 과제 상태를 확인하므로 중지 중엔 403). 과제가 다시 편집 가능해지면(유예 연장·재개) **새 QR 없이 자동
   재개**된다.
4-2. **다른 연구원이 같은 기기를 연결**(그 연결이 승인되는 시점): 이전 연구원의 그 기기 과제 연결을 **모두 끊고**, 그 기기에서
   작성 중이던 이전 연구원 노트를 WEB으로 되돌린다(이력 사유 "다른 연구원이 기기 연결"). 책임자 목록에는 "끊김". 앱 쪽의
   "올리지 않은 기록이 있으면 다른 연구원 연결 거부" 규칙은 유지.
4-3. **토큰 만료·다시 연결**: 14일 오프라인으로 토큰이 만료돼도 과제 연결은 유지된다. 앱의 "다시 연결"은 **기기 재인증 요청**을
   보내고, 연구원 본인 웹 대시보드에 승인 모달이 뜬다(3.3과 같은 모달·10분). 승인하면 새 토큰이 발급되고 **아직 살아 있는 과제
   연결이 모두 그대로** 쓰인다(책임자 재발급 불필요). 재인증 요청 코드는 기기가 이미 가진 기기 ID·연구원으로 묶이며, 살아 있는
   과제 연결이 하나도 없으면 재인증 대신 "연구책임자에게 과제 QR을 요청하세요" 안내.
4-4. **장기 미접속**: 마지막 접속 후 **30일**이 지나면 그 기기의 모든 과제 연결을 끊고 노트를 WEB으로 되돌린다(사유 "장기 미접속").
4-5. **사용 중지(분실)**: 연구원(마이페이지) 또는 책임자(과제별 끊기)가 할 수 있다. 마이페이지의 사용 중지는 그 기기의 **모든** 과제
   연결을 즉시 끊고 노트를 WEB으로 되돌린다. 다시 쓰려면 과제별 QR부터.
5. 토큰: 기기·연구원 단위 토큰은 유지하되, 모든 노트·버전 API가 **(기기, 연구원, 과제) 연결이 활성인지** 확인한다.
   과제가 연결 안 됨 → 403 `PROJECT_NOT_LINKED`(이름은 작성자 판단 가능, 계약에 확정). 기존 `NOT_EDIT_OWNER`·
   `NOT_WRITABLE` 규칙은 유지.
6. 기관 스위치가 꺼지면 지금처럼 모든 `/api/app/v1`이 403 `APP_DISABLED`, 웹 발급 영역은 안내.
7. 마이페이지의 "태블릿 연결"(연구원 스스로 QR 발급)은 **제거**. 마이페이지에는 **내 기기 목록(기기별 연결된 과제 표시)과
   사용 중지만 남긴다**(작성자 판단, 4-5 규칙).

## 5. 동기화 주기

| 항목 | 지금 | 바꿈 |
|---|---|---|
| 주기 동기화 | 60초 | 10분 |
| 자동 버전(손을 4초 이상 멈췄을 때) | 5분 | 30분 |
| 토큰 갱신 | 동기화마다 | 하루 1번, 또는 만료까지 남은 기간이 짧을 때(기준은 작성자 판단) |

즉시 동기화는 유지: 노트를 나갈 때, 앱을 내릴 때, 버전 저장·작성 완료, 네트워크 복귀, 앱 다시 열기.
승인 대기 중 상태 확인은 별도(짧은 간격, 10분 안에 끝남).

## 6. 바뀐 쪽만 올리기

- 앱이 버전을 만들 때 페이지별 PNG의 해시를 이전 버전과 비교해, **같으면 이전 버전의 이미지 ref를 그대로 쓴다**.
  바뀐 페이지만 새 ref·새 바이트.
- 업로드에는 새 ref의 바이트만 담고, 재사용 ref는 서버에 이미 있는 파일을 가리킨다. 서버는 이미 같은 ref·같은 바이트면
  다시 쓰지 않고 다른 바이트면 400을 내도록 되어 있으므로(2C), **재사용 ref가 업로드에 바이트 없이 오는 경우**를 받아들이도록
  계약·서버를 맞춘다: 그 ref가 같은 노트에 이미 저장돼 있으면 통과, 없으면 400(앱은 전체를 다시 보낸다).
- 내용 해시(계약 §6)는 지금과 같은 정의를 유지하되, 재사용 ref의 바이트는 서버가 저장된 파일에서 읽어 계산한다.
- 기기 저장소도 같은 바이트를 페이지마다 중복 저장하지 않는다.

## 7. 제약

- 단방향: 서버는 기기에 노트 내용·획 데이터를 보내지 않는다(메타데이터만).
- 기존 노트·버전 데이터 형식과 웹 표시는 그대로(바이트 동일 렌더링).
- Java 8, 기존 보안 체인·오류 형식·IP 실패 제한·클라이언트 IP 규칙(X-Real-IP) 유지.
- 2C에서 정한 계약 원칙 유지: 계약 문서(SYNC-API.md) = 서버 동작 = 모의 서버.
- 온프렘: 서버는 기관 내부망 HTTPS, QR의 서버 주소는 `app.base-url`(태블릿에서 닿는 주소). 연결 방향은 기기 → 서버만.

## 8. 작성자에게 맡김

- DB 구조(과제 연결 표, 승인 요청 표, 기존 `PL_APP_DEVICE`·`PL_APP_PAIRING_CODE`와의 관계), 마이그레이션은 다시 실행해도
  안전하게.
- 대시보드 모달의 빠른 반영 방식(폴링 간격 / 웹 푸시), 앱의 승인 대기 폴링 방식.
- 오류 코드 이름(계약 문서에 확정).
- 과제 종료·구성원 제외 감지 시점(요청 시 검사 / 일괄 작업).
- 기존 연결(계정 단위로 이미 연결된 기기)의 이행 방법 — 개발 단계라 운영 데이터는 없다고 보고 단순하게 처리해도 된다
  (작성자 판단, 배포 문서에 적기).

## 8-1. 작성자 판단으로 정한 것 (검토 후 바꿀 수 있음)

- 토큰은 **승인 후에** 발급한다. pair 응답은 "승인 대기" 상태와 대기 확인용 일회성 값만 주고, 앱은 그것으로 상태를 확인하다가
  승인되면 토큰을 받는다(승인 전 토큰으로 할 수 있는 일이 없게).
- 앱 확인 단계("{과제명} / {연구원}으로 연결할까요?")의 과제명·연구원 이름은 코드를 **소모하지 않는 조회**로 가져온다(같은 IP
  실패 제한 적용). 실제 연결(코드 사용)은 "연결"을 누를 때.
- 오류 코드 이름은 계획에서 확정해 계약 문서에 적는다(예: `PROJECT_NOT_LINKED`, `PAIRING_PENDING`, `PAIRING_REJECTED`,
  `PAIRING_EXPIRED`, `PROJECT_SUSPENDED`).
- 기존 계정 단위 연결은 개발 단계 데이터뿐이라 이행 시 **모두 끊고 과제 QR로 다시 연결**하게 한다(배포 문서에 명시).
- 대시보드 모달: 대시보드 진입 시 + 대시보드에 머무는 동안 짧은 주기 확인(웹 푸시는 이번 범위 밖).

## 9. 부하 추정 (참고)

기기 100대, 동시 필기 30명, 버전 1개 ≈ 1MB 가정:
- 요청: 초당 약 0.3~0.4건(지금의 1/5 수준), 토큰 갱신 하루 100건.
- 업로드: 시간당 60~90개 → 바뀐 쪽만 올리기 적용 시 저장량은 페이지 수·수정 범위에 비례해 더 줄어든다.
- 주된 비용은 요청이 아니라 버전 그림 저장 공간이었고, 이번 변경(주기·바뀐 쪽만)으로 줄인다.
